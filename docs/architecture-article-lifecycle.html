ATL Content Network — How Articles Reach The Browser

Architecture reference for new team members. Updated May 2026.

1. The Two Repos

atomic-content-platform (this repo) — All code: Dashboard (Next.js), Content Pipeline (Node), Site Worker (Astro). Deployed to CloudGrid + Cloudflare Workers.

atomic-labs-network (data repo) — Pure data: configs, articles (markdown), overrides. Zero code. Git is the database.

2. Article Creation — How An Article Gets Into Git

Two paths: Automated (scheduler) or Manual (dashboard trigger)

↓

↓
Quality ScoreClaude scores 1-10
↓
Git Commitarticles/slug.md → staging branch
→
n8n WebhookTriggers AI image generation

BullMQ Job Queue manages this. Three phases (since the resilience update):

  • Phase 1 — LLM Generation: Calls Claude to write the article. Results cached in Redis so retries skip this.
  • Phase 2 — Git Push: Commits the markdown file to the staging branch. This is where rate limits hit.
  • Phase 3 — n8n Image: Fires webhook for AI image generation (fire-and-forget).

If Phase 2 fails (GitHub rate limit), BullMQ retries only Phases 2+3. The expensive LLM call is NOT repeated.

⚠ Key insight: Markdown is converted to HTML at seed time, NOT at request time. The Worker never parses markdown. This is why KV has pre-rendered HTML — zero processing at the edge.

5. Serving a Request — The Worker

5a. Homepage (travelswire.com/)

3 KV reads total: hostname lookup + config + article index
BrowserGET travelswire.com/
↓
MiddlewareKV: site:travelswire.com → siteId
↓
MiddlewareKV: site-config:travelswire → config
↓
index.astroKV: article-index:travelswire → all metadata
↓
Astro SSRSorts → Hero + What's New + Must Reads + More On
↓
BrowserHTML rendered, cache: 60s edge

Homepage sections are computed from the single article-index array:

  • Hero: Tagged as "hero" (or newest N if none tagged)
  • What's New: Next N newest after hero
  • Must Reads: Tagged as "must-read" (random fallback from remaining)
  • More On: Everything else, paginated (Load More button calls /api/articles)

All sections are disjoint — an article appears in exactly one section.

5b. Article Page (travelswire.com/best-movies-2026)

4 KV reads: hostname + config + full article body + article index (for related)
BrowserGET /best-movies-2026
↓
Middlewarehostname → siteId → config (2 KV reads)
↓
[slug]/index.astroKV: article:travelswire:best-movies-2026
↓
Inject Pipeline1. Inline ads → 2. Video embeds → 3. Scripts
↓
BrowserFull article, cache: 300s edge

Three injection steps happen at request time on the pre-rendered HTML body:

  • Inline ads: Inserts ad slots at configured positions (after-paragraph-3, etc.)
  • Video embeds: Inserts responsive YouTube iframes from frontmatter videos array
  • Scripts: Injects per-article tracking/analytics scripts into <head> and body

7. Failure Modes — What Happens When Things Break

GitHub goes down / rate limited

Live sites: Zero impact. Worker reads from KV, never from GitHub. Sites keep serving.

New content: Stops flowing. Articles can't be committed to Git. BullMQ retries with backoff.

Dashboard: Slowed — reads use tree cache (60s TTL) and retry+throttle, but may timeout.

Cloudflare KV outage (extremely rare)

site:hostname lookup fails → 500 for all pages. No fallback — Worker is fail-closed.

But: KV is replicated across 300+ edge PoPs. Outages are near-zero. In 5 years, maybe 2 incidents.

sync-kv.yml fails (Action error, rate limit)

Sites keep serving old content from KV. No visible error. Content is just stale until sync recovers.

This is actually the best failure mode — sites never go down, they just show slightly old data.

Article in Git but not in KV

Visitor gets 404 for that specific slug. The Worker has no way to read from Git.

Fix: Wait for sync-kv to run (auto on next commit to main), or manually run pnpm seed:kv <siteId>.

9. Key Facts To Remember

  • Worker never reads Git. All data comes from KV. Git is the authoring layer only.
  • Markdown → HTML happens at seed time (in seed-kv.ts), not at request time.
  • One article-index key holds ALL article metadata for a site — homepage reads this one key.
  • One article:siteId:slug key holds the full pre-rendered HTML for one article detail page.
  • Multi-tenant: One Worker deployment serves ALL sites. site:hostname KV key maps to the right config.
  • Config is 5-layer merged: org → groups → overrides → site. Merged at seed time, stored flat in KV.
  • Cache: homepage 60s, articles 5min, errors never cached.

10. Future Proposal — KV Size Optimization

🔮 Investigate: Evict Old Unpublished Article Bodies

Currently seed-kv writes ALL articles to KV — including old drafts. As sites grow to 200+ articles, the article-index key gets large and KV write volume grows. This is a proposal to investigate, not an urgent fix.

1. Measure current KV usage per site
Write a script to measure: how many articles per site, total bytes in article-index, total bytes in individual article keys. Establish baseline. Current estimate: ~400KB per site at 79 articles. Need to know the real numbers before optimizing.
2. Never evict published articles
Published articles are indexed by Google and linked from social media. Removing them from KV = 404 for live URLs = SEO damage. The article:siteId:slug key MUST stay for any article with status: "published", regardless of age.
3. Keep article-index complete (metadata is tiny)
The article-index key is a JSON array of metadata (~100 bytes per article). At 500 articles, that's ~50KB — negligible. Never trim the index — homepage, search, and categories need it to show all content.
4. Candidate for eviction: draft/review article bodies older than 6 months
Articles with status: "draft" or status: "review" that haven't been published in 6+ months are invisible to visitors anyway. Their full HTML body (article:siteId:slug key, ~5-20KB each) could be skipped during seed-kv to save write volume. The article-index entry stays — only the body key is omitted.
5. On-demand hydration if evicted article is published
If a draft is later published, the next sync-kv run would write the body key. Between publish and sync, the article would 404 — same as any newly committed article before sync runs. Acceptable latency (usually seconds to minutes).
6. Investigate KV billing impact before acting
Cloudflare KV pricing is per-read and per-write, NOT per-storage-GB (free tier: 1GB, paid: $0.50/GB-month). The bigger cost driver is write volume during sync, not stored bytes. Measure whether fewer writes actually saves money before building eviction logic. It may not be worth the complexity.
