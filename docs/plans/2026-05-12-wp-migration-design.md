# WordPress → ATL Content Network Migration Design

**Date:** 2026-05-12
**Scope:** Migrate 50 WordPress sites to the ATL content network platform
**Status:** Approved

---

## Context

The ATL content network currently runs on a dev Cloudflare account with test sites. 50 production WordPress sites need to migrate to this platform. All 50 domains are already managed in Cloudflare. After migration, WordPress is decommissioned entirely — the ATL platform becomes the sole content system, with git as the source of truth.

### Data Source

A CSV/Numbers spreadsheet with 10 columns per site:

| Column | Maps to |
|---|---|
| Name | `domain` + site folder name |
| Website Category | `brief.vertical` |
| Menu Items | Navigation categories + article tag mapping |
| IAB Top Categories (Vertical) | `brief.vertical` + `brief.iab_categories` |
| Sub Categories | `brief.sub_categories` |
| Color Palette | `theme.colors.*` |
| Logo | Download → `assets/logo.png` |
| Favicon | Download → `assets/favicon.png` |
| Posts REST API (articles) | WP REST API endpoint for article ingestion |
| GA Info | `tracking.ga_property_id`, `tracking.ga_measurement_id`, `tracking.gtm_id` |

---

## Approach: CSV-Driven Batch Pipeline (3 phases)

### Phase 1: Site Scaffolding (minutes)

Parse CSV → create all 50 site folders with `site.yaml`, download logos/favicons, register in `dashboard-index.yaml`, create `staging/<domain>` branches. sync-kv.yml fires automatically.

### Phase 2: Article Ingestion (hours)

Per site: fetch WP REST API → `turndown` HTML→MD → Claude cleanup/category-mapping → Gemini hero image generation → upload images to R2 → commit `.md` files to git → sync-kv.yml syncs to KV.

### Phase 3: Verification & Cutover (per site)

Automated + manual QA on staging preview. When verified, register Worker Custom Domain via CF API → DNS flips from WP to our Worker.

## Article Conversion

### Per-Article Pipeline

```
WP REST API JSON
    │
    ├─ turndown: content.rendered (HTML) → clean Markdown    [free, deterministic]
    ├─ Claude Sonnet: cleanup shortcodes, map categories,    [~3,200 input + 550 output tokens]
    │                 fix/generate description
    ├─ Gemini 2.0 Flash: generate hero image from            [$0.039/image]
    │                    title + description
    ├─ Upload image → R2 directly                            [not stored in git]
    └─ Assemble .md file with frontmatter → commit to git
```

### WP JSON → ATL Frontmatter Mapping

| WP JSON field | ATL frontmatter field | Logic |
|---|---|---|
| `title.rendered` | `title` | Direct copy, HTML-decoded |
| `excerpt.rendered` | `description` | Strip HTML tags; Claude generates if empty |
| `slug` | `slug` | **Exact match** — preserves URLs for SEO |
| `date` | `publishDate` | Format as YYYY-MM-DD |
| `yoast_head_json.author` | `author` | From Yoast metadata |
| `categories` (WP IDs) | `tags` | Fetch WP category names → map to Menu Items from CSV |
| `content.rendered` | markdown body | `turndown` HTML→MD + Claude cleanup |
| `yoast_head_json.og_title` | `seo.og_title` | Preserved for SEO continuity |
| `yoast_head_json.og_description` | `seo.og_description` | Preserved |
| `yoast_head_json.canonical` | `seo.canonical` | Preserved |
| `yoast_head_json.twitter_card` | `seo.twitter_card` | Preserved |
| featured image | `featuredImage` | New image generated by Gemini, stored in R2 |
| `id` | `wp_original_id` | Audit trail |

### Image Handling

- Hero images are **generated by Gemini** (not copied from WP) — own the images, no copyright risk
- Stored directly in **R2** (`<siteId>/assets/images/<slug>.webp`), not in git
- Frontmatter references R2 path: `featuredImage: /assets/images/<slug>.webp`
- Worker serves via existing R2 asset route: `<domain>/<siteId>/assets/images/...`
- Logo and favicon downloaded from WP URLs (per CSV), stored in git `sites/<domain>/assets/`

The fetcher paginates automatically using `X-WP-TotalPages` header. Fetches **all** articles, not just 75.

## Testing & QA

### Layer 1: Unit Tests (Vitest)

| Test | Verifies |
|---|---|
| CSV parser | All 10 columns parsed correctly, edge cases handled |
| HTML→MD converter | Clean markdown from WP HTML (paragraphs, lists, images, shortcodes, Elementor) |
| Frontmatter builder | Valid YAML from WP JSON + Yoast, matches `ArticleFrontmatter` interface |
| Category mapper | WP category IDs → correct Menu Item names, case-insensitive, fallback handling |
| Slug validator | Filename matches WP slug, handles unicode/long/special-char slugs |
| Color parser | CSV color string → `theme.colors` object |
| GA info parser | CSV GA string → separate tracking fields |
| Site.yaml generator | CSV row → valid site.yaml |

### Layer 2: Integration Tests (per-site, after import)

| Check | Pass criteria |
|---|---|
| Article count match | WP total === `.md` files committed |
| Slug integrity | Every WP slug has matching `.md` file |
| Frontmatter completeness | All required fields present in every article |
| No empty bodies | Every article has >100 chars of markdown body |
| Image existence | Every `featuredImage` exists in R2 |
| Category coverage | Every article has ≥1 tag matching CSV Menu Items |
| SEO fields present | og_title, og_description, canonical non-empty |
| Date validity | All dates valid, not future |
| No duplicate slugs | Unique slug per article |
| KV sync successful | `sync-status:<siteId>` exists with `ok: true` |

### Layer 3: E2E Verification (before DNS cutover)

#### Automated

- Homepage renders (200, contains site name, shows hero articles)
- All articles render (200 for every slug on staging)
- Category pages render with correct articles
- Images load from R2
- SEO meta tags present in `<head>`
- No 404 internal links
- GA tracking scripts present

#### Manual QA Checklist (per site)

- Homepage: hero, articles, navigation menu
- Each category page: correct article filtering
- 5 random articles: formatting, image, author, date, reading time
- Side-by-side comparison with WP original (same slug, equivalent content)
- Mobile responsive
- Logo and favicon display
- Theme colors match CSV
- Page source: SEO meta tags

## DNS Cutover & Rollback

### Production CF Account — Worker Isolation

| Resource | Name | Isolation |
|---|---|---|
| Worker | `atomic-site-worker` | Unique name, doesn't touch existing workers |
| KV namespace | New: `atl-config-prod` | New namespace ID, isolated |
| R2 bucket | New: `atl-assets-prod` | Unique bucket name |
| Custom Domains | Per-site registration | Only affects explicitly registered domains |

### Cutover Sequence (per site, ~30 seconds)

1. Register Worker Custom Domain via CF API (DNS flips automatically)
2. Verify: `curl -I https://<domain>` returns 200
3. Update `dashboard-index.yaml`: `status: "Live"`, `custom_domain: "<domain>"`

### Rollback Options

**Option A — Quick rollback (<1 min):** Delete Worker Custom Domain registration via CF API. DNS reverts. Traffic returns to WP (if still running).

**Option B — Point DNS elsewhere:** Update DNS record manually to maintenance page or WP IP.

**Decision tree:** KV missing → re-run sync-kv. R2 missing → re-run seed:kv. Worker 500 → check logs, fix, redeploy. Config wrong → edit site.yaml, push. Unfixable in 15 min → rollback to WP.

### Cutover Schedule

| Week | Action | Sites |
|---|---|---|
| Week 1 | Pilot | 1 site (travelbeautytips.com), monitor 7 days |
| Week 2 | Batch 1 | 5 sites, monitor 3 days |
| Week 3 | Batch 2 | 15 sites, staggered cutover (5/day) |
| Week 4 | Batch 3 | 29 remaining sites (10/day) |
| Week 5 | Stabilization | Monitor all 50, fix issues |

### WP Decommission Timeline

- Day 0: DNS cutover
- Day 1-7: WP still running (rollback safety net)
- Day 7: Mark WP as "can decommission"
- Day 14: Stop WP hosting
- Day 30: Delete WP data

## Slug Preservation (SEO Critical)

WP slug from JSON maps directly to article `.md` filename and Worker `[slug]` route. URLs stay identical:

- WP: `tvshowbox.com/newsom-slams-trump-secretary-sean-duffy-over-reality-tv/`
- ATL: `tvshowbox.com/newsom-slams-trump-secretary-sean-duffy-over-reality-tv`

Trailing slash handled by CF redirect rules.
