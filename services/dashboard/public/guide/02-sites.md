# Sites: Creating, Editing, and Deploying

## Site Lifecycle

Every site moves through these statuses:

```
Staging --> Ready --> Live
```

| Status | Meaning |
|--------|---------|
| **Staging** | Wizard completed. Site files committed to a staging branch, KV seeded, Worker preview available |
| **Ready** | Staging merged to main. Production KV seeded. No custom domain yet |
| **Live** | Custom domain attached to the production Worker and DNS verified |

## Creating a Site (Wizard Flow)

The dashboard wizard at `/wizard` has five steps:

### Step 1: Identity
- **Site name** and **tagline**
- **Pages project name** (becomes the site folder in the data repo)
- **Company** (ATL or NGC) and **Category** (tier-1 IAB category from the Content Aggregator)

### Step 2: Niche Targeting
- **Category** (tier-1) and **Subcategories** from the Content Aggregator
- **Tags** — search and select or create new ones
- Or **select an existing bundle** to reuse a preconfigured niche

### Step 3: Content Brief
- **Audience** description, **tone**, **topics** (auto-suggested by AI)
- **Content guidelines** (free-form)
- **Schedule**: articles per day, preferred days

### Step 4: Theme
- **Base theme**: modern, editorial, bold, or classic
- **Logo**: auto-generated by Gemini with background removal, or upload custom

### Step 5: Preview
- Review all settings before committing

### Step 6: Go Live
- Commits `site.yaml`, `skill.md`, and asset directories to a `staging/{project}` branch in the data repo
- Seeds the site into CONFIG_KV so the Worker can serve it
- Shows the Worker Preview URL (`?_atl_site=<domain>` on the staging Worker)

## What Gets Created

When the wizard completes, the following files are committed to the data repo:

```
sites/{project-name}/
  site.yaml          -- full site configuration
  skill.md           -- AI agent instructions derived from the brief
  assets/
    logo.png         -- generated or uploaded logo (optional)
  articles/
    .gitkeep
```

And in the data repo root:

```
dashboard-index.yaml -- updated with the new site entry
```

## site.yaml Structure

```yaml
domain: my-travel-site
site_name: "Wanderlust Weekly"
site_tagline: "Your guide to the world"
pages_project: my-travel-site
groups:
  - travel          # editorial vertical
  - premium-ads     # ad partner config
active: true
brief:
  audience: "Adventure travelers aged 25-45"
  tone: "conversational"
  article_types:
    listicle: 40
    standard: 30
    how-to: 20
    review: 10
  topics:
    - Destination Guides
    - Travel Tips
    - Local Culture
  seo_keywords_focus: []
  content_guidelines:
    - "Focus on practical advice"
    - "Include budget estimates"
  review_percentage: 5
  schedule:
    articles_per_day: 2
    preferred_days: ["Monday", "Wednesday", "Friday"]
    preferred_time: "10:00"
  vertical: Travel          # legacy name — maps to tier-1 category
  vertical_id: "abc123"     # Content Aggregator tier-1 category ID
  category_ids: ["abc123", "def456"]  # all targeted category IDs
theme:
  base: modern
  logo: /assets/logo.png
  favicon: /assets/logo.png
```

## Staging Branch Workflow

Each site gets a dedicated staging branch: `staging/{project-name}`.

1. **All edits go to staging first** -- config changes, new articles, logo updates
2. **Preview URL** -- The staging Worker serves the site via `?_atl_site={domain}` (no per-site Pages deploy needed). The `sync-kv.yml` workflow syncs staging branch commits to CONFIG_KV.
3. **Go Live / Publish** -- merges staging to `main`, which triggers `sync-kv.yml` to update production KV
4. **Branch reset** -- after merge, staging is deleted and recreated from `main` HEAD so it is clean for the next edit cycle

## Editing an Existing Site

From the site detail page (`/sites/{domain}`), operators can:

- **Edit config** (name, tagline, brief, theme) -- updates `site.yaml` on the staging branch
- **Generate/upload logo** -- commits to `assets/logo.png` on staging
- **Delete articles** -- removes markdown files from staging
- **Publish staging** -- merges staging to main for production

All edits trigger a rebuild on the staging branch for preview before publishing.

## Attaching a Custom Domain

1. Site must be in **Ready** status (staging merged to main, production KV seeded)
2. From the site detail page (Identity tab), enter the custom domain
3. Dashboard registers the domain as a Worker Custom Domain on the production Worker
4. Seeds `site:{customDomain}` into production KV so the Worker resolves it
5. Set up DNS: CNAME record pointing to the Worker hostname
6. Status updates to **Live** once DNS is verified

## Deleting a Site

Deletion performs a full cleanup across Git, KV, and R2 — removing all site files, article and shared-page KV entries, override files, and R2 assets. Sites go to trash first and can be restored or permanently deleted.

For the complete deletion flow, resource inventory, and error handling details, see the **Deleting a Site** guide page.
